## 想做成什么

最初的愿景是把工科学生实际使用的工程软件连接起来，并提供原生 agent 接口，帮助他们理解、计算、建模、分析和修订工程。长期需要可扩展到多个软件和学科，近期必须有一个完整、值得使用的产品任务。

产品方向是独立桌面 App。学生仍可在熟悉的原生 CAD 中编辑；App 应承担什么职责、何时值得实现，需要你根据实际工作流决定。FreeCAD 与 SOLIDWORKS 都在第一批宿主范围；一位机械学生反馈主要在 SOLIDWORKS 中做图纸，所以不应要求所有用户迁移到 FreeCAD。这是需求线索，尚不是经过验证的市场结论。

项目发起人是计算机专业学生，缺少机械工程经验。请自行作出推荐、说明依据与不确定性，不把技术选型、工况设计和验收方案全部变成反问。需要外部专业判断或 Windows 实机时，给出最小验证任务、所需材料、通过与失败标准。

目前最大的偏离风险是继续堆计算工具、接口、报告和验收脚本，却没有清晰回答：学生为什么打开这个产品，带来什么工程，最后完成什么。请从这个问题重新组织项目，允许质疑已有实现；不要因为代码已经存在就把所有模块都塞进首版。

## 截至本次交接的事实

- 已有 FreeCAD 原生三段轴闭环：当前对象读取、显式工况绑定、候选直径比较、事务写入、撤销、人工接续与保存重开。仅支持明确结构，不能接管任意零件。
- 七段课程输出轴包含键槽和圆角，可读取当前尺寸并做受限校核及右轴肩圆角修改；未开放任意 agent 改径。
- 22 个 stdio MCP 工具已实现；当前工程工具与任务书批处理工具需要严格区分。批处理能导出 STEP/DXF/PDF/DOCX，但不是已有原生图纸的同步编辑。
- CalculiX 梁任务包含当前轴快照、查询、取消和结果适用性；不代表三维局部应力、完整疲劳、制造或整机认可。部分材料、系数、配合和载荷来源仍缺独立核实。
- Linux ARM64 FreeCAD 1.1.4 已完成真实界面与 MCP 混合旅程：MCP 改径 40→35 mm、界面原生撤销至 40 mm、Sketcher 手改为 38 mm、MCP 拒绝旧候选、界面保存退出重开、MCP 继续改到 36 mm。MCP 来自测试客户端；没有把它当作学生试用。
- macOS Qt 辅助功能点击崩溃仍在。WorkBuddy 曾完成真实 MCP 调用，本轮 Linux 接续尝试因客户端界面未响应而未完成；不能把过去的客户端调用拼成这次全流程通过。
- SOLIDWORKS 只有只读 VBA 采集源码和 JSON 检查器：活动零件、配置、原始尺寸标识、已打开工程图的模型与配置引用。枚举完整性未确认、尺寸尚未映射为轴段，没有 Windows 编译或实机证据，也没有原生写入、重建、撤销和图纸同步。
- 本机全量 `python -m pytest -q` 在 2026-10-28 返回 480 passed、1 skipped（环境未安装官方 MCP SDK，相关客户端测试跳过）。这是当次本地结果，不等于远端 CI、目标用户环境或专业验收。测试命令使用项目依赖齐备的 Python 3.13 环境。
- 独立 App、普通学生可理解的条件输入、真实学生试用尚未交付。本地模型、会话和运行产物不包含在源码包内。

## 请作出明确决策

1. **首个完整任务**：比较少量可行候选，选一个。建议审查“学生修订已有传动轴与关联工程图”：打开原文件 → 提交修订要求 → 核对尺寸与工况 → 比较候选 → 确认原生修改 → 检查图纸标注 → 撤销/保存/继续手改。你可以否决，但须给出更有价值且能落地的替代故事。
2. **独立 App 的职责与软件分工**：学生在哪个窗口完成每一步？哪些仍交给 CAD？外部 MCP 客户端是否应继续成为必经步骤？给出最小交互流程和数据流，不先做视觉稿。
3. **宿主与操作系统顺序**：FreeCAD、Windows SOLIDWORKS、macOS、Linux 如何排序？首版只支持哪些原生特征与配置？Windows 环境暂不可用时哪些工作仍能推进、哪些必须停止。
4. **专业输入和工程语义**：学生不应手写复杂 SI JSON。怎样从任务书、原模型、材料说明中获得条件并确认缺失项？几何不能推断的载荷、支承、限值如何处理？怎样建立尺寸—轴段—工程图标注的明确对应。
5. **可靠修改与图纸完成标准**：定义预览、确认、修改、重建、原生 Undo、保存和重开的行为。SOLIDWORKS 零件与图纸分别处理；核对配置、引用、覆盖显示值及悬空尺寸，不用 PDF 文件存在代替图纸正确。
6. **工程计算边界**：哪些检查首版有用且依据可取得，哪些应延期？如何同时表达数值结论、方法适用范围、输入来源和当前模型适用性，避免把 agent 做成只会报“受阻”的工具。
7. **现有代码去留与最小架构**：按实际目录给出保留、修剪、修改、冻结、必要新增项。复用计算能力，但不要预建通用 CAD 框架、插件市场或兼容层。
8. **扩展条件**：怎样从机械切入保留多软件、多学科的长期方向？给出接入下一种软件的进入条件，不能用工具数量衡量产品价值。

## 要交付的规划

- 一句话产品定义、首批用户、完整用户故事与首版不做事项。
- 当前实现差距表，引用读过的代码路径；事实、推断和待验证项分开。
- 与 CAD 自带功能及少量现有 AI 工程工具比较，说明学生为何值得单独使用本产品；当前产品能力以官方资料为准。
- 推荐架构与一张组件/数据流图，说明关键选型和被放弃方案的理由；涉及当前第三方能力时查官方公开资料。
- 分阶段路线图，每阶段交付可以实际使用的软件能力，写清依赖、验收、失败后决策和不能声称的成果。
- 下一开发阶段的具体任务清单：文件/模块、输入输出、验收命令、真实使用检查、完成与停止条件。优先级由你判断，给出足够让执行者直接开工的第一步。
- 少量必须通过学生或机械专业人员验证的关键假设，以及低成本验证方法；不以泛泛“先调研”搁置全部开发。

规划阶段不启动实现、发布、付费或对外联系；当前开发阶段不新增前端，但允许规划后续独立 App 的进入条件。保护原始工程和手工修改，不以无约束重写代替必要修剪。遇到证据或环境缺口时，完成其余独立可规划部分，精确列出缺口，不能编造验证结果或要求发起人代做专业方案。
